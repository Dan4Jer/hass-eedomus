- (direction) Regle (AGENTS.md, decision utilisateur 2026-10-04) : tout texte en anglais — logs, docstrings, commentaires, libelles utilisateur ; le francais n'existe que comme traduction, jamais en dur
- (decision) Langue de repli : anglais — la traduction FR doit etre complete avant livraison (decision utilisateur)
- (decision) Mecanisme du panneau custom : le backend expose les chaines via une commande websocket (source unique cote Python), le panneau lit la locale (hass.locale) et demande ses chaines — HA ne sert pas les traductions d'un panneau custom (decision utilisateur)
- (note) Etat constate (audit 2026-10-04) : le panneau JS porte ~42 chaines utilisateur toutes en francais code en dur (microcopie, chips, statuts, aria-labels), aucun mecanisme de locale ; en.json manque la section ui que fr.json possede ; services.yaml est en anglais non localise (pas de section services dans strings.json) ; replis d'entites en anglais dur (Unknown Device) ; logs et docstrings massivement en francais
- (capability) CAP-1 Inventaire i18n : chaque chaine utilisateur de l'integration est cataloguee avec sa surface, son mecanisme cible (translations backend, commande websocket panneau, logs/docstrings) et sa cle ; l'inventaire est le livrable de l'audit et la reference de la migration. Success : toute chaine user-facing du repo figure dans l'inventaire avec mecanisme + cle, et aucune chaine codee en dur n'est oubliee (verifie par grep croise).
- (capability) CAP-2 Traductions backend completes et structurellement identiques : en.json est la source de verite, fr.json en reproduit la structure exacte (y compris la section ui manquante aujourd'hui) ; les descriptions de services passent par la section services de strings.json ; les replis d'entites (Unknown Device) sont localises. Success : en.json et fr.json ont le meme arbre de cles (test), les services et les replis d'entites s'affichent dans la langue de HA.
- (capability) CAP-3 Chaines du panneau via websocket : le backend expose un catalogue de chaines localisees via une commande websocket ; le panneau charge ce catalogue selon la locale et n'embarque aucune chaine utilisateur en dur ; repli anglais quand la locale n'est pas couverte. Success : aucune chaine user-facing en dur dans www/eedomus-panel.js (grep), le panneau s'affiche en anglais sous HA anglais et en francais sous HA francais.
- (capability) CAP-4 Source anglais partout : logs, docstrings et commentaires de l'integration sont en anglais. Success : aucun message de log ni docstring en francais dans custom_components/eedomus (grep), les logs de l'instance live s'affichent en anglais.
- (constraint) Mecanismes natifs HA uniquement : strings.json + translations/*.json pour le backend ; pas de lib de traduction tierce dans le panneau (vanilla JS, no build) ; la source unique des chaines du panneau vit cote Python (commande websocket), jamais dupliquee dans le JS
- (constraint) Les contrats gels restent intacts : les formes de reponse de eedomus/get_peripherals et eedomus/get_coherence ne changent pas pendant la migration (seules les chaines d'affichage migrent) ; les periphriques eedomus gardent leur nom cloud (donnee, pas libelle)
- (note) Non-goals : pas de nouvelle fonctionnalite (renommage de l'onglet Historique et onglet infos-box = specs/UX separes) ; pas d'infrastructure multi-langues au-dela de en/fr ; pas de traduction des donnees utilisateur (noms cloud, valeurs) ; le panneau ne force jamais la locale - il suit HA
- (question) Strategie de migration des logs/docstrings existants : tout-en-un (une passe complete) vs anglais-pour-le-nouveau + migration au toucher (plus lent mais zero risque) - a trancher a l'inception de l'epique
