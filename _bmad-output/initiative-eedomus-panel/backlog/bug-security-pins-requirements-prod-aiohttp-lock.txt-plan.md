## Intent

**Problem:** The 0.15.5 dependency batch missed two files: `requirements_prod.txt` still pins `aiohttp==3.14.3` — exactly inside the vulnerable range of the 8 open aiohttp alerts (CVE-2026-111064, -111065, -111066, -111748, -111749, -111750, GHSA-2g87-pp6c-29x5, CVE-2026-111063) — and it is copied into the HACS release package by `release.yml:48`, so the published 0.15.5 ships a vulnerable pin. `requirements.lock` is a stale pip-compile artifact (`aiohttp==3.9.3`) consumed by nothing.

**Approach:** Bump `requirements_prod.txt` to `aiohttp==3.14.5` (the pinned line already on unstable for every other requirements file), delete `requirements.lock` as a dead artifact (autogenerated by a pip-compile flow the repo does not use, referenced by no workflow or script), and add a guard test that scans the tracked requirements surfaces and fails on any pin matching the vulnerable ranges this ticket documents. Scope of the 0.15.6 release.

## Boundaries

- Only `aiohttp` needs the bump in `requirements_prod.txt`: its other pins (requests==2.34.2, yarl==1.25.1) match the other requirements files on unstable and appear in no open alert.
- The manifest runtime floors are untouched: HA provides aiohttp at install; the manifest floor is not the alert surface.
- The guard test uses the explicit vulnerable pin list of this ticket (exact pins, matching the alerts' exact ranges), not a live API — no network in tests.

## Acceptance Criteria

1. **Malformatted pin refused**
   **Given** the tracked requirements surfaces (requirements.txt, requirements_dev.txt, requirements_prod.txt, requirements-test.txt, pyproject.toml)
   **When** the guard test scans them
   **Then** none carries `aiohttp==3.14.3` or `black==26.10.0` — the two vulnerable pins of the open alerts — and the test fails with the offending file and pin if one appears
2. **The shipped file is clean**
   **Given** requirements_prod.txt
   **When** read
   **Then** it pins `aiohttp==3.14.5` (or newer), matching the rest of the release line
3. **The lock is gone, explicitly**
   **Given** requirements.lock (stale, unconsumed)
   **When** the fix lands
   **Then** the file is deleted — the decision is recorded here, not left silent
4. **No regression**
   **Given** the full suites
   **When** they run
   **Then** unit and node suites stay green and the format gate passes

## Implementation Notes

Oneshot: one pin line, one file deletion, one guard test — no subagent needed. The lock deletion is safe: its header documents a pip-compile flow no workflow invokes, and the only requirements file any workflow consumes is `requirements_prod.txt` (release.yml:48, package copy only).
